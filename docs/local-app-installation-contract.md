# Runstir 로컬 앱 설치·목록 계약

상태: 2026-10-09 사용자 승인. 직접 설치와 2차 목록·이력의 설계 계약이다.
정본: [결정: 로컬 앱 목록·버전 선택과 설치 파일 직접 실행의 답](https://github.com/minjunkim-dev/mobile-runtime/issues/189#issuecomment-6080134494).
문서 작성 기준: main `7b009337cded75e1d6ed2f6f92a4e074cd9792e1`.
선행 계약: [공통 CLI 계약](./cli-expansion-common-contract.md), [준비 계약](./cli-expansion-preparation-contract.md), [지원·검증 계약](./cli-expansion-support-contract.md), [GUI 계약](./gui-workflow-contract.md).

사용자와 Q1~Q11을 결정했다. 마지막 Q10~Q11에도 사용자가 “추천대로”라고 답했다.

이 답은 설계 계약이다. 제품 구현·실제 설치·기기 실행·접근성 검증·출시 준비 완료를 뜻하지 않는다. 중간의 Android 실기기 필수 검증 제안은 Q6 수정 승인이 대체한다.

## 1. 출시 단계

첫 Runstir 1.0.0은 CLI·GUI·로컬 앱 파일 직접 설치·실행을 함께 제공한다. 로컬 앱 목록·설치 이력·보유 파일 버전 선택은 2차다. 2차의 미완료를 첫 1.0.0 출시의 차단 조건으로 만들지 않는다. 원격 팀용 앱 센터는 별도 선택적 범위다. 서버·계정·CI를 로컬 사용에 필수로 추가하지 않는다.

## 2. 첫 지원 파일과 설치 대상

첫 호스트는 macOS Apple Silicon이다. iOS Simulator용 `.app`, 설치 조건을 충족한 iOS 실기기용 `.app`·`.ipa`, Android Emulator·연결 실기기용 단일 `.apk`를 입력으로 지원한다. 같은 파일 확장자만으로 호환성을 인정하지 않는다. 플랫폼·기기 종류·architecture·OS·서명 조건을 확인한다. 부적합한 파일은 이유를 표시하고 중단한다.

iOS 실기기의 첫 직접 설치는 Development·Ad Hoc으로 서명한 조건 충족 파일로 제한한다. Enterprise·MDM과 App Store·TestFlight 배포 연동, AAB·split APK 묶음·범용 압축 파일 자동 해석은 첫 직접 설치 범위에서 제외한다. IPA 처리는 안전한 압축 구조 검사와 원본 서명 보존을 전제로 한다.

Development·Ad Hoc IPA는 대상 기기의 UDID가 provisioning profile에 포함돼야 한다. 개발자 계정에 기기를 등록해도 기존 IPA가 바뀌지는 않는다. 필요한 경우 해당 기기를 포함한 profile로 앱을 다시 서명·내보내야 한다. 신뢰·Developer Mode 등 해당 설치 경로의 조건도 충족해야 한다. Runstir는 기기 등록을 대행하거나 앱을 자동 재서명하지 않는다. 설치 조건을 갖추는 수동 단계에는 필요한 행동과 다시 확인을 제공한다.

로컬 `devicectl` 도움말의 앱 설치 입력은 `.app`다. IPA 내부 `.app`의 추출·설치 경로는 후속 명세·구현·실제 검증에서 확인한다. 공식 플랫폼 설치 가능성이 Runstir 구현 완료의 증거는 아니다.

## 3. CLI·GUI와 소스 없는 흐름

CLI와 GUI 모두 `파일 확인 → 실행 기기 선택 → 변경 내용 확인·승인 → 설치 → 실행`을 공통 Swift Core에서 처리한다. GUI 전용 판정·설치 로직을 만들거나 터미널 문장을 파싱하지 않는다. 기존 Adapter/provider와 ProcessRunner를 재사용한다. 구체 CLI 명령 이름·옵션·Core API·JSON/progress 표현은 후속 명세에서 정한다. 기존 공개 CLI·JSON 호환 계약을 유지한다.

프로젝트 소스와 계정을 필수로 요구하지 않는다. 파일이나 기기를 고른 것만으로 설치를 시작하지 않는다. 소스 빌드와 환경 준비를 자동으로 시작하지 않는다. 외부 개발 서버가 필요한 앱 파일은 그 조건과 실행 결과를 표시한다. 서버나 소스 연결을 임의로 만들지 않는다. 서버 조건을 충족하지 못한 상태를 앱 정상 동작으로 표시하지 않는다.

## 4. 파일 정보·설치 전 검사와 승인

앱 이름·플랫폼·앱 ID·표시 버전·빌드 번호·파일 경로·출처·파일 내용 식별값·기기 종류·architecture·OS·확인 가능한 서명 조건을 표시한다. 앱 ID는 iOS bundle ID 또는 Android package name이다. 앱 이름이나 표시 버전과 구분한다. 사용자 등록 파일의 제작 출처를 임의로 Runstir 빌드로 표시하지 않는다. 파일 경로나 내용 식별값을 제작자 신뢰·안전성 증거로 쓰지 않는다.

파일 정보 확인을 위해 포함된 스크립트를 실행하지 않는다. 명확한 부적합은 설치 전에 중단한다. 필수 파일 정보나 실행 기기의 준비 조건을 확인하지 못하면 중단하고 필요한 행동과 다시 확인을 제공한다. 앱 이름·표시 버전 같은 선택적 표시 정보가 없으면 확인 불가로 표시한다. 사전 검사와 플랫폼이 최종 수락하는 실제 설치 결과를 구분한다.

설치 직전에 파일 내용·기기·기존 앱 상태와 교체 계획을 다시 확인한다. 승인 뒤 파일·대상·변경 내용이 바뀌면 다시 검사하고 승인받는다. 다른 파일이나 다른 기기로 조용히 전환하지 않는다.

## 5. 기존 앱 교체와 데이터

같은 앱이 이미 설치된 경우 앱 ID·기존 버전·새 버전·대상 기기·교체 내용을 표시하고 승인받는다. 관측할 수 없는 기존 상태도 명시한다. 플랫폼의 데이터 보존 재설치를 시도한다. 자동 삭제·초기화와 실패 뒤 삭제 재설치는 하지 않는다.

이전 버전 설치에는 별도 경고와 승인을 요구한다. 플랫폼이 거부하면 이유를 표시하고 중단한다. 이전 버전 설치 성공과 앱 데이터 보존을 보장하지 않는다. 설치 전 상태로 자동 복구됐다고 표시하지 않는다. 실제 표본의 교체와 데이터 유지 증거를 확인한다.

## 6. 앱 파일 작업과 병렬 실행

실제 앱 파일 경로마다 작업 창을 둔다. 같은 실제 파일을 다시 열면 기존 창을 사용한다. 경로 별칭과 `.app` bundle의 실제 경로 식별은 명세에서 정한다. 내용이 같은 파일이 다른 경로에 있다는 이유로 원본을 합치거나 이동하지 않는다. 원본 내용이 바뀌면 기존 창에서도 다시 검사한다.

한 앱 파일 작업은 한 번에 한 실행 기기에서 한 변경 작업을 수행한다. 다른 앱 파일 작업과 프로젝트 작업은 독립 실행 기기·로그·상태로 병렬 실행한다. CLI와 GUI가 공통 Core의 기기·앱 교체·자원 충돌 판정을 사용한다. 다른 작업이나 실행 중인 앱과 충돌하면 소유 작업과 이유를 표시하고 중단한다. 자동 기기 전환·기존 작업 종료·대기 큐와 같은 파일의 여러 기기 일괄 실행을 첫 범위에 추가하지 않는다.

## 7. 설치·실행 결과와 실패·취소

파일 확인·설치 완료·실행 요청 완료·관측 가능한 앱 실행 상태·실패·취소를 구분한다. 설치 완료는 해당 앱이 설치된 상태로 관측한 결과다. 실행 명령 성공만으로 첫 화면 도달이나 앱 기능 정상 동작을 표시하지 않는다. 첫 화면 도달은 실제 검증 표본에서 별도 증거로 확인한다.

실패·취소·연결 해제 뒤에는 실제 기기 상태를 다시 확인하고 남은 단계와 변경 계획을 표시한다. 파일·대상·변경 내용이 달라지면 다시 승인받는다. 완료한 설치와 기존 데이터를 보존한다. 다른 기기로 자동 전환하거나 앱을 자동 삭제하지 않는다.

취소·창 닫기·Runstir 종료는 기존 GUI 계약을 그대로 따른다. 취소는 해당 작업의 새 단계를 중단한다. 도구가 안전한 중단을 지원하지 않으면 대기 상태와 이유를 표시한다. 기존 자원과 다른 작업을 보존한다. 창 닫기는 작업 계속 또는 취소 후 닫기를 선택하게 한다. 전체 종료는 진행 중인 작업을 표시하고 기존 계약의 선택을 제공한다. 실행 완료한 앱을 창 닫기만으로 중단하지 않는다. 명시적 종료와 소유 자원 정리는 기존 플랫폼별 계약을 따른다.

## 8. 2차 목록·버전 선택과 이력

사용자가 등록한 파일과 Runstir 빌드 성공 산출물을 목록에 기록한다. 전체 디스크를 자동 검색하지 않는다. 원본을 복사·이동하지 않고 경로·내용 식별값·읽은 metadata를 기록한다. 파일이 사라지거나 바뀌면 다시 확인한다. 설치 실패만으로 유효한 빌드 산출물을 목록에서 지우지 않는다.

앱은 플랫폼과 앱 ID로 묶는다. 같은 이름이나 표시 버전만으로 파일을 합치지 않는다. 내용 식별값·기기 종류·architecture·배포 방식이 다르면 별도 후보로 표시한다. 사용자가 구체 파일과 기기를 선택한다. 버전 이름을 임의로 정렬해 최신 파일을 자동 설치하지 않는다. 버전 선택은 보유 파일의 재설치다. 소스 checkout·재빌드·이전 버전 설치 성공을 뜻하지 않는다.

이력에는 파일 식별·대상 기기·시각·설치/실행의 관측 결과와 실패·취소를 기록한다. 이력을 현재 기기 설치 상태의 정본으로 사용하지 않는다. 재설치 전에 현재 파일과 기기 상태를 검사한다. 앱 환경값·비밀값을 목록 정보에 저장하지 않는다.

사용자가 목록·이력 기록을 삭제할 수 있게 한다. 기록 삭제로 원본 파일이나 기기 앱을 삭제하지 않는다. 첫 범위에서 자동 보존 기간·자동 정리를 도입하지 않는다. DB 스키마·파일 보관·전체 로그 정리의 세부 구현은 후속 명세에서 정한다.

## 9. 직접 설치의 실제 검증 기준

1. 지원 형식·설치 경로의 대표 파일로 실제 CLI와 GUI의 파일 확인·기기 선택·승인·설치·실행·첫 화면을 확인한다. iOS Simulator `.app`, Android Emulator 단일 `.apk`, iOS 실기기 `.app`/`.ipa`의 Development·Ad Hoc 경로를 구분한다.
2. 부적합 파일·필수 확인 불가·지원 제외 형식·기기/architecture/OS 불일치·서명/profile 문제·IPA 압축 처리·교체/이전 버전 거부를 확인한다. 자동 재서명·기기 등록·삭제·초기화가 없는지 확인한다. parser/validation fixture와 실제 기기 실행 증거를 구분한다.
3. 같은 앱 교체의 표본 데이터 유지, 실패·취소·연결 해제·파일 변경 뒤 상태 재관측·재승인·재실행을 확인한다. 기존 설치나 다른 작업을 자동 종료·삭제하지 않는지 확인한다.
4. 독립 파일·프로젝트의 병렬 실행, CLI·GUI의 충돌 판정·작업별 취소·창 닫기, 같은 입력의 검사·변경 계획·후보·결과 일치를 확인한다. 키보드·포커스·VoiceOver·승인/실패 안내를 실제로 확인한다.
5. 2차 목록은 중복 버전의 서로 다른 파일·파일 변경·이동/삭제·실패/취소 이력·기록 삭제의 원본 보존을 별도 검증한다. 2차 미완료는 첫 1.0.0의 차단 조건이 아니다.

기존 네이티브·Flutter·React Native의 여섯 Simulator/Emulator 조합을 유지한다. iOS 직접 파일 설치에는 대표 실기기의 실제 검증을 추가한다. 이는 전체 프레임워크 실기기 행렬을 요구하는 결정이 아니다.

사용자는 Android 실기기를 보유하지 않는다. Q6 수정 승인에 따라 첫 출시는 Android Emulator 검증을 필수로 둔다. Android 실기기는 미검증으로 표시하며 기기 확보 후 USB/RSA 승인·직접 설치·연결 해제를 검증한다. Android 실기기 구매·대여·클라우드 테스트를 첫 출시 필수 조건으로 만들지 않는다. 클라우드 APK 실행을 로컬 Runstir USB 경로의 증거로 세지 않는다.

파일·기기·OS·architecture·도구·서명 방식과 실행 결과를 증거에 고정한다. 한 표본의 성공을 모든 기기·OS·프레임워크의 성공으로 일반화하지 않는다. 배포 파일의 실제 설치·GUI/CLI 실행과 공동 출시 판정은 별도 공동 게이트에서 연결한다. CI·문서·디자인으로 실제 설치·화면·접근성 증거를 대신하지 않는다.

CLI 명령·입력·Core API·JSON/progress·잠금·파일 식별·DB·fixture·검증 표본의 구체값은 후속 명세에서 정한다. 제품 구현·SDK 설치·기기 실행·공개 배포는 별도 작업이다. CONTEXT.md에는 승인한 용어만 기록한다. 문서 병합을 제품 구현이나 실제 검증의 증거로 사용하지 않는다.
