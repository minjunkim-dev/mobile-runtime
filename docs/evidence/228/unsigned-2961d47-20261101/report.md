alpha.16으로 네이티브 Android 최소 앱 Todo와 OSS 앱 Now in Android(NIA)를 CLI·GUI 4개 경로에서 다시 실행해 올바른 첫 화면과 정상 종료를 확인했습니다. alpha.15에서 #360으로 실패한 빈 SDK root 준비도 Todo 첫 화면까지 완료했습니다. 이 문서는 #228의 alpha.16 실제 실행·경계·보존 검증을 기록합니다. 최종 head의 독립 리뷰·CI와 병합 상태는 PR·이슈에 별도로 기록합니다.

후보는 `b3b699aa016349afba9ada38c14f80ae4a2263d137b7eeaa95f384880bcfb9d1`, 제품 source는 `2961d4763f443566fbf7ef68e6158e4d321b53d0`입니다(#224 alpha.16 고정). CLI·GUI 실행 파일과 후보 metadata의 SHA-256은 시작 때 고정값과 같았고 제품 코드는 수정하지 않았습니다. alpha.15 결과는 승계하지 않았습니다. #370(down 뒤 `pidof` 해석)은 후보 제작 시점에 열려 있어 사용자 결정으로 넣지 않았습니다. 호스트는 macOS 27.2 arm64, Emulator 37.1.11, API35 Google APIs arm64 r9 image, 고정 AVD `Runstir225_cli35`·`Runstir225_gui35`입니다.

| 앱 | CLI | GUI | 준비 |
| --- | --- | --- | --- |
| Todo `:app/debug` | "You have no tasks!" 첫 화면, down이 앱 중지·claim 해제, 5초간 PID 부재 | 같은 첫 화면, 종료가 앱 중지·claim 해제, PID 부재 | 설치 항목 없는 계획 승인 → 완료. 빈 SDK root에서 패키지·image·AVD 생성 뒤 Runstir가 켠 AVD에서 첫 화면 |
| NIA `:app/demoDebug` | For you 관심 주제 첫 화면, down이 앱 중지·claim 해제, 5초간 PID 부재 | 같은 첫 화면, 종료가 앱 중지·claim 해제, PID 부재 | CLI `--module :app --variant demoDebug`와 GUI 선택 칸이 모두 target을 reuse로 해석, 승인 뒤 완료 |

각 행은 alpha.16용 별도 full Git clone이고 HOME·TMPDIR을 새로 만들었습니다. 의존성·빌드 산출물을 복사하지 않았습니다. JDK·SDK·Gradle user home·고정 AVD는 기존 것을 써서 cold-cache 결과로 세지 않습니다. 고정 AVD는 이전 후보의 앱 데이터가 남아 있고 `-no-window`로 미리 부팅했으므로 제품 cold boot 증거가 아닙니다. 별도로 Runstir가 새로 만든 AVD를 Runstir `up`이 직접 켜고 `down`이 그 Emulator를 종료했습니다. 원래 도구만 쓴 기준선은 후보와 무관해 이번에 다시 실행하지 않았습니다(alpha.15 기록 참조).

**빈 SDK root (#360 재검증).** 빈 소유 SDK root·AVD home의 새 Todo clone에서 setup 계획은 alpha.15와 같은 SDK package 6개와 이후 AVD 생성을 냈습니다. 라이선스 기록 없이 승인하면 아무것도 받지 않고 waiting-manual이었고 완료·변경 파일이 없었습니다. 사람 단계로 기존 검증 SDK의 같은 hash 기록 `android-sdk-license`를 재사용했습니다(새 동의 없음, #204와 같은 절차). 승인하자 build-tools 34.0.0·cmdline-tools 23.0·emulator·platform-tools·platform 35가 설치됐고(276.6초), image만 라이선스 수동 단계로 남아 partial로 끝났습니다. 같은 방식으로 image의 `android-sdk-arm-dbt-license` 기록을 재사용한 뒤 image가 설치됐고(287.6초), 새 계획이 pixel_7·API35 AVD 생성을 고정해 승인 뒤 만들었습니다(67.5초). 재계획은 모두 reuse였고, `up`이 그 AVD를 직접 켜서 Todo 첫 화면을 띄웠으며(73.9초) `down`이 앱 중지·Emulator 종료·claim 해제를 보고했습니다.

**#361 남은 claim.** alpha.15 #228 NIA 실행이 남긴 claim 2개(cli35·gui35)를 먼저 바이트 그대로 보존했습니다. cli35를 켠 뒤 그 앱이 다시 실행된 상황을 만들려고 수집기가 `am start`로 NIA를 띄웠습니다. Todo `up`은 단계 전에 거부됐고, 안내가 소유 프로젝트 경로와 `mobile down --platform android`를 알려 줬습니다. 안내대로 소유 프로젝트(alpha.15 NIA clone)에서 alpha.16 `down`을 실행하자 active run 기록 없이도 그 앱만 force-stop하고 claim을 해제했습니다(`android.claim stopped`, logcat `Force stopping`). 그 뒤 Todo `up`이 성공했습니다. gui35의 claim은 Emulator가 꺼진 동안 소유 프로젝트 `down`이 보존하며 "AVD를 켠 뒤 다시 down"을 안내했고, 켠 뒤 다시 실행하자 해제했습니다. 4개 경로와 새 AVD 경로의 `down`은 모두 `android.claim stopped`를 냈고 claim 파일이 남지 않았습니다. 같은 AVD에서 다른 프로젝트의 다음 `up`도 막히지 않았습니다.

**#362·#366 대상 선택.** NIA 기본 doctor·setup은 모듈 둘(`:app`, `:app-nia-catalog`) 때문에 target을 수동으로 남겼습니다. `mobile setup --module :app --variant demoDebug --plan`은 target을 reuse로 해석했고 승인 뒤 완료됐으며, 같은 선택의 build·up이 실제로 설치·실행했습니다. 콜론 없는 `--module app`도 같은 plan-id를 냈습니다. 모르는 `--module :nope`와 `--variant nope`는 계획 단계에서 사용 가능한 목록과 함께 실패했고 완료·변경 파일이 없었습니다. 근거 문구는 옵션이면 `explicit android.module=:app; explicit android.variant=demoDebug`, 추적되지 않는 `mobile.yml`이면 `mobile.yml android.module=:app; …`였습니다. mobile.yml 위에 `--variant prodDebug`를 주면 `mobile.yml android.module=:app; explicit android.variant=prodDebug`였습니다. 옵션 값이 mobile.yml과 같으면 mobile.yml로 표시하는데, PR #367이 plan-id 유지를 위해 정한 동작입니다. 확인 뒤 mobile.yml은 지웠습니다. GUI 준비 계획은 화면에서 고른 `:app`/`demoDebug`를 써서 같은 explicit 근거로 reuse를 냈고, alpha.15와 달리 mobile.yml을 요구하지 않았습니다.

**실행 경계.** 두 번째 빈 SDK root에서 build-tools 다운로드 중 SIGINT는 130/cancelled였고 자식 `curl`이 남지 않았으며, SDK root에 stage나 부분 파일이 남지 않았고 재계획은 그 package를 여전히 설치 대상으로 냈습니다. NIA `up`의 Gradle 단계 중 SIGINT는 130/cancelled였고 Gradle 자식(java 2개)이 남지 않았습니다. 그러나 취소된 `up`이 claim 없는 기기 예약을 남겼습니다. 같은 AVD의 Todo `up`은 "result … is unconfirmed"로 거부되며 이미 끝난 operation을 멈추라고 안내했고, 소유 프로젝트 `down`은 모든 항목 skipped로 예약을 남겼습니다. 소유 프로젝트에서 `up`을 다시 하자 성공했고 그 `down`이 claim을 해제했습니다. Runstir `down`만으로 복구되지 않고 안내가 복구 경로를 말하지 않아 #373으로 분리했고 예약 파일은 손대지 않았습니다. 같은 AVD에 두 clone이 동시에 `up`하면 뒤 요청은 앞 작업·프로젝트·pid를 밝히며 단계 전에 거부됐고 앞 작업은 성공했습니다. 없는 variant의 build는 변경 전에 `android.target` 미준비로 실패했습니다. GUI build 전후 Emulator의 설치 identity가 같아 build가 설치하지 않았고, 실행 뒤 바뀌었습니다. 모든 경로에서 추적 source·index·flags가 보존됐습니다.

GUI에서 Android build가 끝나면 기기 칸이 비고 비활성화되는 결함(#353)을 다시 재현했습니다. Todo는 build 전에 기기를 고르지 않아 실행이 "실행할 기기를 선택하세요"로 멈췄고, 환경 다시 확인으로 칸을 되살려 기기를 고른 뒤 실행했습니다. NIA는 build 전에 고른 숨은 선택으로 실행이 완료됐습니다. GUI 작업 취소(#358)와 같은 SDK root 동시 승인은 이번에 다시 실행하지 않았습니다.

AC06은 실제 Mac의 HVF 가속(`android.emulator.acceleration` reuse, `-accel-check` HVF)과 기존 환경 반복으로 확인했습니다. 보존 기준 VM은 guest의 kern.hv_support가 0이라 실행하지 않았습니다. Android 실기기는 미검증입니다(AC19). Emulator 성공을 로컬 USB/RSA 검증으로 바꾸지 않았습니다.

수집 오류를 제품 실패와 분리해 보존했습니다. NIA `down`에 `--module`·`--variant`를 넘긴 수집기 인수 오류(제품이 변경 전에 "Omit build and device selectors"로 거부), 이전 Emulator 종료 직후 같은 adb 포트 범위를 검사해 gui35 수집기가 시작 전에 멈춘 일, 남은 adb 서버 때문에 cli35 재부팅 수집기가 한 번 멈춘 일이 여기에 해당합니다. Emulator console 인증 사본은 #226·alpha.15와 같은 수집기 전제로 입력 HOME에 복사했다가 정리 때 지웠습니다. 다른 AVD(cli37·gui37)에 남은 alpha.14 #225 RN claim 2개는 이번 범위 밖이라 그대로 두었습니다.

AC02는 빈 SDK root 준비·라이선스 대기·부분 완료·image·AVD 생성과 NIA 대상 선택, AC03은 취소·동시 대상·잘못된 variant·module·active-run 보호와 남은 claim 정리, AC04는 같은 입력의 CLI·GUI 결과와 build의 설치 없음, AC05는 4개 fresh clone 첫 화면, AC06은 실제 Mac 가속과 기존 환경 반복에 연결합니다. AC15의 같은 후보 연결과 AC17의 실패 이력 보존을 유지합니다(alpha.15 결과는 `results-224.json`의 이전 묶음과 저장소의 #228 alpha.15 증거에 남음). 이 정본은 #224 alpha.16 정본 위에 #228의 네이티브 Android 범위를 더합니다. AC05 경로 4개와 새 요구 7개(AC02 2개·AC03 2개·AC04 2개·AC06 1개)가 pass이고, AC03 NIA에는 #373을 미해결로 남겼습니다. 현재 결과는 pass 12개, fail 0개, unverified 39개입니다. alpha.16의 다른 프레임워크 게이트는 아직 실행하지 않았고 unsigned 배포 제한도 있어 공동 출시 판정은 blocked입니다. 전체 공동 게이트와 서명·공증·공개 판정은 별도로 남습니다.
