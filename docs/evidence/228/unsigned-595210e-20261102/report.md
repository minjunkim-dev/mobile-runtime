alpha.17로 네이티브 Android 최소 앱 Todo와 OSS 앱 Now in Android(NIA)를 CLI 경로에서 다시 실행해 올바른 첫 화면과 정상 종료를 확인했습니다. 빈 SDK root 준비는 Todo 첫 화면까지 다시 완료했습니다. alpha.17에 새로 들어간 #370(PR #371·#372)과 #373(PR #375) 수정은 실제 AVD에서 확인했습니다. GUI 경로는 GUI 조작 권한 요청이 거부되어 실행하지 않았습니다. 이 문서는 #228의 alpha.17 실제 실행·경계·보존 검증을 기록합니다. 최종 head의 독립 리뷰·CI와 병합 상태는 PR·이슈에 별도로 기록합니다.

후보는 `5b987003fb2b89a2c7bf75087512d135c0d9b63f47a38dd0b4a518ce4e7b532e`, 제품 source는 `595210e8d3e6249b879388005a318543c0ce778a`입니다(#224 alpha.17 고정). CLI·GUI 실행 파일과 후보 metadata의 SHA-256은 시작 때 고정값과 같았고 제품 코드는 수정하지 않았습니다. alpha.16 결과는 승계하지 않았습니다. 실행 전에 검사 조건을 `requirements-before-execution`에 먼저 기록했습니다. 호스트는 macOS 27.2 arm64, Xcode 27.2, Emulator 37.1.11, API35 Google APIs arm64 r9 image, 고정 AVD `Runstir225_cli35`·`Runstir225_gui35`입니다. 시작 전에 두 AVD를 쓰는 Emulator·claim·다른 세션 작업이 없음을 확인했습니다.

| 앱 | CLI | GUI | 준비 |
| --- | --- | --- | --- |
| Todo `:app/debug` | "You have no tasks!" 첫 화면, down이 앱 중지·claim 해제, 5초간 PID 부재 | 미실행 | 설치 항목 없는 계획 승인 → 완료. 빈 SDK root에서 패키지·image·AVD 생성 뒤 Runstir가 켠 AVD에서 첫 화면 |

각 행은 alpha.17용 별도 full Git clone이고 HOME·TMPDIR을 새로 만들었습니다. 의존성·빌드 산출물을 복사하지 않았습니다. JDK·SDK·Gradle user home·고정 AVD는 기존 것을 써서 cold-cache 결과로 세지 않습니다. 고정 AVD는 이전 후보의 앱 데이터가 남아 있고 `-no-window`로 미리 부팅했으므로 제품 cold boot 증거가 아닙니다. 별도로 Runstir가 새로 만든 AVD를 Runstir `up`이 직접 켜고 `down`이 그 Emulator를 종료했습니다. 원래 도구만 쓴 기준선은 후보와 무관해 다시 실행하지 않았습니다(alpha.15 기록 참조).

**빈 SDK root.** 빈 소유 SDK root·AVD home의 새 Todo clone에서 setup 계획은 alpha.16과 같은 SDK package 6개와 이후 AVD 생성을 냈습니다. 라이선스 기록 없이 승인하면 아무것도 받지 않고 waiting-manual이었고 SDK root가 비어 있었습니다. 사람 단계로 기존 검증 SDK의 같은 hash 기록 `android-sdk-license`를 재사용했습니다(새 동의 없음, #204와 같은 절차). 승인하자 build-tools 34.0.0·cmdline-tools 23.0·emulator·platform-tools·platform 35가 설치됐고(282.9초), image만 라이선스 수동 단계로 남아 partial로 끝났습니다. 같은 방식으로 image의 `android-sdk-arm-dbt-license` 기록을 재사용한 뒤 image가 설치됐고(281.7초), 새 계획이 AVD 생성을 고정해 승인 뒤 만들었습니다(66.3초). 재계획은 설치 항목이 없었고, `up`이 그 AVD를 직접 켜서 Todo 첫 화면을 띄웠으며(57.8초) `down`이 앱 중지·Emulator 종료·claim 해제를 보고했습니다.

**#373 취소된 up의 reservation (PR #375).** NIA `up`의 Gradle 단계 중 SIGINT는 130/cancelled였고 Gradle 자식(java 2개)이 남지 않았습니다. alpha.16과 달리 NIA 프로젝트의 reservation·claim 파일이 남지 않았고, 바로 뒤 같은 AVD에서 다른 프로젝트(Todo)의 `up`이 막히지 않고 성공했습니다. NIA `up`이 성공해 claim이 있는 상태에서 다시 한 `up`을 Gradle 단계 중 취소하자 이전 claim이 같은 operation·앱으로 복원됐고(키 순서만 다름) 실행 중인 앱도 그대로였습니다. 그 뒤 `down`이 앱 중지와 claim 해제를 보고했습니다. 남은 reservation의 거부 안내도 실제로 봤습니다. 수집기 전제(아래)를 빠뜨린 Todo 첫 `up`이 빌드 뒤 기기 식별 단계에서 실패해 claim 없는 reservation을 남겼습니다. 기기에 닿은 뒤의 실패라 #375 설계대로 보존된 것입니다. 이때 NIA `up`은 단계 전에 거부됐고, 안내가 소유 프로젝트 경로에서 `mobile up --platform android --device 'avd:Runstir225_cli35'` 다음 `mobile down`을 하라고 알렸습니다. 안내대로 Todo에서 다시 한 `up`이 그 reservation을 대체해 성공했고 `down`이 claim을 해제했습니다.

**#370 다른 앱을 가리키는 claim (PR #371·#372).** 자연 발생 경로를 만들 수 없어 단위 테스트와 같은 전제를 수집기가 만들었습니다. Todo `up` 뒤 그 claim의 appID만 설치된 NIA로 바꾸고 NIA를 띄웠습니다. 제품 코드와 claim의 다른 필드는 건드리지 않았습니다. `down`은 Todo를 `android.app stopped`로 멈추고, claim이 NIA를 가리키며 이번 down이 멈춘 Todo가 아니라서 보존한다고 밝혔습니다. 기록된 장치가 남지 않았으니 다시 down하면 NIA를 관측해 정리하고, AVD가 꺼졌으면 먼저 시작하라고 안내했습니다. AVD를 끈 상태의 `down`은 claim을 보존하며 AVD를 켠 뒤 다시 실행하라고 안내했습니다. AVD를 켜고 NIA를 띄운 뒤의 `down`은 남은 claim 경로로 NIA만 force-stop하고(logcat `Force stopping`) claim을 해제했으며, 5초간 NIA PID가 다시 나타나지 않았습니다. 정상 경로의 `down` 5회는 force-stop 뒤 `pidof` 결과를 중지로 읽고 claim을 해제했습니다.

**#362·#366 대상 선택.** NIA 기본 doctor·setup은 모듈 둘(`:app`, `:app-nia-catalog`) 때문에 target을 수동으로 남겼습니다. `mobile setup --module :app --variant demoDebug --plan`은 target을 `explicit android.module=:app; explicit android.variant=demoDebug` 근거의 reuse로 해석했고 승인 뒤 완료됐으며, 같은 선택의 build·up이 실제로 설치·실행했습니다. 콜론 없는 `--module app`도 같은 plan-id를 냈습니다. 모르는 `--module :nope`와 `--variant nope`는 계획 단계에서 사용 가능한 목록과 함께 실패했고 완료·변경 파일이 없었습니다. mobile.yml 근거 문구는 이번에 다시 실행하지 않았습니다.

**실행 경계.** 두 번째 빈 SDK root에서 build-tools 다운로드 단계 중 SIGINT는 130/cancelled였습니다. 신호 시점에 자식 프로세스가 없었고(alpha.16은 `curl` 1개) 남은 프로세스와 SDK root의 stage·부분 파일도 없었으며, 재계획은 그 package를 여전히 설치 대상으로 냈습니다. 같은 AVD에 두 clone이 동시에 `up`하면 뒤 요청은 앞 작업·프로젝트·pid를 밝히며 단계 전에 거부됐고 앞 작업은 성공했습니다. 없는 variant의 build는 변경 전에 `android.target` 미준비로 실패했습니다. 모든 경로에서 추적 source·index·flags가 보존됐습니다.

**GUI 미실행.** GUI clone 둘과 입력은 만들었고 Runstir.app을 Todo 입력으로 띄웠습니다. GUI 조작 권한 요청이 거부되어 아무 조작 없이 종료했습니다. 따라서 GUI의 Todo·NIA 첫 화면(AC05 GUI 2개), 같은 입력의 CLI·GUI 비교(AC04 2개), GUI build 뒤 기기 칸 유지(#353)와 GUI 작업 취소 안내(#358, PR #376)는 alpha.17에서 확인하지 않았습니다.

AC06은 실제 Mac의 HVF 가속(`android.emulator.acceleration` pass, Hypervisor.Framework)과 기존 환경 반복으로 확인했습니다. 보존 기준 VM은 guest의 kern.hv_support가 0이라 실행하지 않았습니다. Android 실기기는 미검증입니다(AC19). Emulator 성공을 로컬 USB/RSA 검증으로 바꾸지 않았습니다.

수집 오류를 제품 실패와 분리해 보존했습니다. Emulator console 인증 사본을 Todo 첫 `up` 전에 만들지 않아 그 `up`이 기기 식별 단계에서 실패했습니다(위 #375 확인에 쓰임). 수집기 셸이 `--platform android`를 한 인수로 넘겨 NIA doctor·setup 6개를 제품이 인수 단계(exit 64)에서 거부했습니다. 빈 SDK root의 첫 `up`은 같은 호스트에 켜 둔 cli35를 adb가 함께 보아 기기 식별 단계에서 멈췄고, cli35를 끈 뒤 다시 실행했습니다. 남은 adb 서버 때문에 cli35 재부팅 수집기가 시작 전에 한 번 멈췄고, 그동안 실행한 `down`은 꺼진 상태 경로를 한 번 더 탔습니다. 인증 사본은 정리 때 지웠고, 정리 뒤 alpha.17 실행의 claim·reservation과 실행 중인 Emulator·GUI가 남지 않았습니다. 다른 AVD(cli37·gui37)에 남은 alpha.14 #225 RN claim 2개는 범위 밖이라 그대로 두었습니다.

AC02는 빈 SDK root 준비·라이선스 대기·부분 완료·image·AVD 생성과 NIA 대상 선택, AC03은 취소·동시 대상·잘못된 variant·module과 남은 claim·reservation 정리, AC05는 CLI fresh clone 첫 화면 2개, AC06은 실제 Mac 가속과 기존 환경 반복에 연결합니다.
