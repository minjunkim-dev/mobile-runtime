## 1. 첫 GUI의 진입과 흐름

첫 Runstir 1.0.0은 CLI와 macOS Apple Silicon GUI를 함께 제공한다. 시작 화면은 `프로젝트 열기`와 `앱 파일 열기`를 제공한다.

프로젝트는 `환경 확인 → 필요한 변경 계획 승인 → 환경 준비 → 플랫폼·실행 기기 선택 → 앱 실행`으로 안내한다. 변경이 없으면 승인과 준비를 생략한다. 환경 확인·환경 준비·빌드·실행·종료도 각각 선택할 수 있다. 폴더나 파일을 고른 것만으로 변경 작업을 시작하지 않는다.

Flutter·React Native의 환경 준비는 iOS와 Android를 모두 포함한다. 앱 실행에서는 플랫폼과 해당 실행 기기를 선택한다. 준비 완료·부분 완료·앱 실행 완료를 구분한다. 여러 후보와 수동 단계는 기존 공통 CLI·준비·지원 계약을 따른다.

로컬 앱 파일은 `파일 확인 → 실행 기기 선택 → 설치·실행`으로 안내한다. 지원 형식·교체·데이터 보존·중복 설치의 상세는 [결정: 로컬 앱 목록·버전 선택과 설치 파일 직접 실행](https://github.com/minjunkim-dev/mobile-runtime/issues/189)에서 정한다. 이 티켓이 해당 계약을 대신하지 않는다.

## 2. 서로 다른 프로젝트와 각 프로젝트의 워크트리

첫 버전부터 독립 프로젝트·워크트리·별도 디렉터리의 병렬 실행을 허용한다. 서로 다른 Git 저장소의 프로젝트와 동일 저장소의 여러 워크트리를 모두 지원한다. 워크트리는 필수가 아니다. 일반 디렉터리도 같은 방식으로 연다.

프로젝트 작업 폴더마다 별도 창을 제공한다. 같은 실제 작업 폴더를 다시 열면 기존 창을 사용한다. 같은 Git 저장소를 공유한다는 이유로 서로 다른 워크트리를 한 창으로 합치거나 병렬 실행을 막지 않는다. 경로 별칭과 symlink의 동일 폴더 식별은 명세에서 정한다.

한 작업 폴더에서는 한 번에 한 변경·실행 명령을 처리한다. 서로 다른 작업 폴더는 실행 작업별 포트·빌드 산출물·로그·상태·실행 기기를 분리하여 병렬 실행한다. 각 실행 작업은 서로 다른 실행 기기를 사용한다. 실행 완료한 앱이 살아 있는 상태와 다음 변경 작업의 충돌을 별도로 관측한다.

GUI 전체를 잠그지 않는다. CLI와 GUI의 같은 프로젝트 변경과 같은 공유 자원 충돌은 공통 Core에서 차단한다. 같은 도구 설치 대상의 동시 변경은 기존 승인형 준비 계약을 따른다. 독립 자원의 작업은 계속 허용한다.

자동 워크트리 생성, 동일 작업 폴더의 여러 기기 일괄 실행·비교, 복잡한 작업 큐와 별도 백그라운드 작업 관리자는 첫 범위에 포함하지 않는다.

## 3. 공유 경계와 자원 충돌

GUI와 CLI가 공통 Swift Core를 직접 사용한다. Core는 탐지·검사·후보·선택 검증·변경 계획·실행·진행·취소·결과·자원 소유권과 충돌 판정을 처리한다. GUI는 입력·승인 화면·상태 표시를 맡는다. 터미널 문장을 파싱하거나 GUI 전용 환경 판정·설치 로직을 만들지 않는다. 외부 도구 호출은 기존 Adapter/provider와 ProcessRunner를 재사용한다.

필요한 개발 서버에는 사용 가능한 포트를 할당한다. 해당 포트를 빌드와 앱 실행까지 전달한다. 프로젝트 파일·lockfile·전역 설정을 자동으로 바꾸지 않는다. 프레임워크나 앱이 별도 포트 전달을 지원하지 않으면 이유를 설명하고 중단한다. 검증하지 않은 방식으로 성공을 표시하지 않는다.

실행 기기는 사용자가 선택한다. 다른 작업이나 실행 중인 앱이 사용하는 기기는 소유 프로젝트와 이유를 표시한다. 사용자가 다른 기기를 선택하거나 기존 작업을 명시적으로 종료한 뒤 다시 확인한다. 다른 기기로 자동 전환하거나 기존 작업을 자동 종료하지 않는다.

같은 프로젝트·같은 설치 대상의 변경 충돌도 소유 작업과 이유를 표시하고 중단한다. 사용자는 기존 작업이 끝난 뒤 상태를 다시 확인하고 재실행한다. 자동 대기 큐는 제공하지 않는다.

기존 공개 CLI·JSON 호환 계약을 유지한다. Core 타입·입력·후보·상태·이벤트·잠금의 구체 API와 JSON/progress 표현은 후속 명세에서 정한다. 병렬 실행을 위한 Core 작업은 CLI와 GUI에서 같은 정책을 구현해야 한다.

## 4. 진행·실패·수동 단계

현재 단계·검사 결과·변경 내용·실패 원인·다음 행동을 기본 화면에 표시한다. 실행 상세 로그는 펼쳐 볼 수 있게 한다. 측정할 수 없는 전체 진행률을 만들지 않는다. warning·unknown을 성공 표시로 바꾸지 않는다. 앱 로그·행동 이벤트 콘솔은 별도 후속 결정의 범위다.

실패 뒤 상태를 다시 확인하고 남은 작업의 변경 계획을 만든다. 계획이 달라지면 다시 승인받는다. 실행 직전에 선택한 실행 기기와 연결·준비 상태를 다시 확인한다. 기기가 사라지면 중단하고 재선택을 받는다.

신뢰·라이선스·개발 설정·서명 등의 수동 단계에는 필요한 행동과 `다시 확인`을 제공한다. 대상이나 승인한 변경 계획이 달라지면 필요한 선택과 승인을 다시 받는다. 기기 삭제·초기화 권한을 추가하지 않는다.

## 5. 작업별 취소·창 닫기·앱 종료

취소는 해당 작업의 새 단계를 중단한다. 완료한 설치와 기존 자원은 보존한다. 안전한 중단을 지원하지 않는 도구는 대기 상태와 이유를 표시한다. 취소가 다른 프로젝트의 작업을 중단해서는 안 된다.

작업 중 창 닫기는 해당 작업의 `작업 계속` 또는 `취소 후 닫기`를 선택하게 한다. 다른 프로젝트의 작업은 계속한다. Runstir 전체 종료는 진행 중인 모든 작업을 표시하고 `작업 계속` 또는 `모두 취소 후 종료`를 선택하게 한다. 안전한 취소가 끝나기 전까지 필요한 창과 상태를 유지한다.

실행 완료한 모바일 앱·기기는 GUI 창 닫기와 Runstir 종료만으로 중단하지 않는다. 명시적 `종료` 작업은 기존 플랫폼별 down·소유권 계약을 따른다. `취소`와 `종료`를 같은 동작으로 표시하지 않는다. 실패나 종료 뒤 정리할 수 있는 자원은 기존 정책에 맞춰 실제 상태와 소유권을 확인한다.

## 6. 배포와 업데이트

GUI는 Developer ID 서명·공증한 DMG로 제공한다. GUI 내부 Core를 함께 배포하여 별도 CLI 설치 없이 동작한다. GUI는 버전과 공식 다운로드 링크를 제공한다. 첫 업데이트는 사용자가 새 DMG로 교체하는 방식이다. 자동 업데이트는 후속 기능이다.

CLI의 Homebrew 설치 경로를 유지한다. GUI용 Homebrew cask는 첫 출시 필수 조건이 아니다. GUI 설치나 업데이트가 별도 설치한 CLI를 자동 교체하지 않는다. 서명·공증과 실제 배포 파일의 실행 검증은 서로 다른 증거다.

## 7. GUI 검증 기준

사용자는 다음을 GUI 구현 완료의 필수 입력으로 승인했다.

1. 서명·공증한 실제 DMG의 설치와 Gatekeeper 우회 없는 실행, 별도 CLI 없는 GUI 동작, 버전·공식 다운로드 링크와 수동 업데이트 경로를 확인한다.
2. 기존 여섯 지원 조합에서 GUI의 환경 확인·준비 승인·기기 선택·빌드·실행·종료를 검증한다. 부분 완료·수동 단계·warning/unknown을 확인한다. Simulator/Emulator 검증은 필수다. 실기기 검증은 필수 출시 조건으로 추가하지 않는다.
3. 서로 다른 프로젝트와 동일 저장소의 두 워크트리에서 병렬 실행을 검증한다. 포트·기기·산출물·로그 분리, 동일 작업 폴더·기기·설치 대상 충돌, 작업별 취소, 창 닫기·앱 전체 종료·실패 후 재확인을 검증한다. 지원 프레임워크의 포트 전달을 확인한다.
4. 기본 흐름의 키보드 조작·포커스·VoiceOver 이름·상태·승인·실패 안내를 실제로 검증한다.
5. 같은 입력의 CLI와 GUI에서 검사·변경 계획·후보·결과·충돌 판정이 일치하는지 확인한다. 로컬 앱 파일 설치 검증은 후속 설치 계약을 연결한다.

CI·문서·디자인만으로 실제 배포·앱 실행·접근성 성공을 대신하지 않는다. 무제한 병렬 성능이나 모든 실기기의 검증은 약속하지 않는다. 구체 fixture·측정·증거 보관과 공동 출시 판정은 명세 및 [결정: CLI·GUI 공동 1.0.0의 출시 게이트와 명세 인계](https://github.com/minjunkim-dev/mobile-runtime/issues/193)에서 정한다.
