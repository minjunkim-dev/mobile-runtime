# 실제 검증의 준비와 수집

실제 후보 게이트를 시작할 때 읽는다. #225에서 발생한 검증 누락·민감 인수 수집·관측기 재시도를 줄이기 위한 절차다. 제품 계약과 승인 범위는 `CONTEXT.md`와 관련 ADR을 따른다.

## 실행 전

1. 후보 ID·제품 SHA·실행 파일 checksum을 확인한다. 티켓 본문과 추가 코멘트의 검증 조건을 기존 증거의 요구 목록에 연결한다. 각 조건의 입력·관측·완료 기준·미검증 상태를 실행 전에 기록한다. 같은 후보의 과거 성공을 재사용하면 fresh clone·cold cache 등 이번 주장의 조건과 맞는지도 구분한다.
2. 자원 소유권·기존 실행·승인 범위와 도구 준비 상태를 확인한다. 환경변수 선언과 실제 daemon·서비스 준비를 구분한다. 큰 네이티브 빌드와 실패·취소 경계는 순차 실행한다. 병렬성 자체가 조건인 경우에는 부하와 공유 cache를 기록하고 결과의 귀속 한계를 남긴다.
3. 관측기의 명령 형태·진행 이벤트·대상 PID 식별을 작은 검사로 먼저 확인한다. 기본값이면 생략되는 인수도 다룬다. 제어할 프로세스는 소유 launcher의 자식 관계와 PID·시작 시각·실행 파일·cwd를 대조한다. 정지·취소 제어는 실패 경로에서도 회수한다. 실제 조건에 도달하지 못한 관측기 오류는 `inconclusive`로 남기고 첫 실행 증거를 소비했는지 구분한다.

## 수집

호스트 프로세스 목록은 아래 도구의 metadata만 저장한다. 명령 인수·환경변수 전체 대신 소유 작업에 필요한 관측만 선택한다. 모호한 실행 파일 이름은 `unresolved`, 파싱하지 못한 행은 `unparsedRows`로 남는다.

```sh
python3 scripts/validation-processes.py
```

이 도구는 PID·부모 PID·CPU·메모리·경과 시간·실행 basename만 수집한다. 자식 프로세스의 인수를 읽지 않는다. 수집 실패 진단에는 원시 도구 출력이나 예외 내용을 넣지 않는다.

비밀값과 개발 연결 인증 경로는 제한 증거에서도 수집 범위를 최소화한다. 필요한 제품 원시 결과는 ADR의 공개·제한 보관 경계를 따른다. `verify-release-evidence.py`의 제한 파일 checksum 성공은 내용의 비밀정보 검사 성공이 아니다. 봉인 전에 내용 검토를 마친다.

## 판정과 전달

- 제품 실패·수집기 실패·판정 불가를 분리하고 이전 시도와 재시도를 보존한다. exit 0만으로 첫 화면을 통과시키지 않는다.
- 숫자는 실행 목록에서 계산한다. 고유 clone 수와 같은 clone의 입력 단계 수를 구분한다.
- Spec 리뷰는 선언된 요구 목록을 티켓·추가 검증 조건과 대조한다. 검사기의 `declared-requirements-only` 결과를 전체 조건의 완전성으로 확대하지 않는다.
- 필수 CI와 추가 관측을 구분하고 SHA·run·attempt·관측 시점을 기록한다. 로컬 watcher 종료와 원격 workflow 취소를 구분한다.
- 인계에는 후보 식별자, 소유 자원과 현재 상태, 승인 범위, 실제 완료·미검증, 실행 중인 검사 세션을 남긴다. 과거 상태를 현재 상태로 쓰지 않는다.

검증 도구의 회귀 검사는 기존 CI의 source-only 자동 탐색에 포함된다.
